# Rediseño de la interfaz — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reorganizar la interfaz en un armazón profesional (barra superior con la acción principal, pestañas, fichas de componente en lugar del mapa de puntos), con paleta auditada clara/oscura y estados distinguibles por forma, dejando lugar para F4–F6.

**Architecture:** Los colores y medidas viven como tokens en `config/palette.css` (claro por defecto, oscuro opcional con `data-theme`). El `app.js` actual (~29 KB) se divide en archivos con una responsabilidad cada uno: `estado.js` (constantes), `iconos.js` (SVG), `dom.js` (utilidades), `modelo.js` (lógica pura sin DOM, probada con Node), `vistas.js` (dibujo) y `app.js` (estado, API, pestañas, eventos). Se construye por etapas: tras cada tarea la app sigue funcionando.

**Tech Stack:** HTML/CSS/JS vanilla (sin frameworks, sin CDN, sin fuentes externas), Flask 3 (Jinja2) para servir; Python para la prueba de paleta; Node (solo para pruebas, ya instalado en la laptop del equipo) para la lógica pura del frontend.

**Spec:** `docs/superpowers/specs/2026-10-22-rediseno-interfaz-design.md` (todo) y decisiones 18, 28, 33, 34 de `docs/DECISIONES.md`.

## Global Constraints

- Sin frameworks JS, sin librerías ni CDN, sin fuentes externas, sin dependencias nuevas de Python (regla del README). Iconos: SVG en línea propios, trazo 1,75 px, `currentColor`.
- Navegadores: Edge, Chrome y Brave recientes (Chromium ≥ 93); sin funciones experimentales.
- **No cambia el contrato de la API** (`/api/scan`, `/api/status`, `/api/guias`, `/api/informe`, `/api/reporte`). El backend no se toca salvo `informe.py` (Tarea 7) y archivos de plantilla.
- Garantías que **no se pueden perder**: nunca datos de ejemplo mostrados como reales (estado vacío al cargar; demostración solo con su aviso); todo texto del sistema escapado (sin `innerHTML` con datos sin escapar); `localStorage` siempre dentro de `try/catch`; recuerda el modo y el tema; el aviso de administrador y el de demostración siguen funcionando; la lista y los textos de `explicador.py` no se cambian.
- Contraste (calculado con la fórmula WCAG): **texto ≥ 4,5:1** y **bordes de controles y elementos de estado ≥ 3:1**, en tema claro y oscuro, comprobado por una prueba automática.
- El estado se distingue por **forma + texto + color** (nunca solo color): `normal` círculo con visto, `advertencia` triángulo, `sospecha` rombo, `critico` octágono con cruz, `no_determinado` círculo discontinuo con interrogación.
- Tema **claro por defecto**; oscuro solo si el usuario lo elige (se recuerda). `[MI LLAMADA]` No se sigue `prefers-color-scheme`: el comportamiento es predecible para presentaciones y proyector.
- Tuteo, textos cortos. Foco visible en todo control, objetivos táctiles ≥ 40 px, respeta `prefers-reduced-motion`.
- Pruebas: `cd backend; python test_scanner.py` (ver `docs/superpowers/plans/COMANDO_PRUEBAS.txt`), estilo `assert`, registradas en `__main__`, stderr limpio. Las pruebas de Node se ejecutan desde `test_scanner.py` con `subprocess` solo si `shutil.which("node")` existe (si no, se omiten en silencio).
- Decisión nueva al final de `docs/DECISIONES.md`: la **39** (solo se agrega). Los números 31 y 32 siguen reservados.
- Verificación visual con captura en el navegador integrado (la hace el controlador) en 1280×720 y ~700 px, tema claro y oscuro.

## Review Focus

1. Un `var(--x)` usado en `style.css` y no definido en `palette.css` deja un elemento sin estilo sin avisar: prueba que cada variable referenciada esté definida (claro y oscuro). → Tarea 1.
2. Valores guardados inválidos en `localStorage` (modo o tema distintos de los permitidos, o el almacenamiento lanza): se usan los valores por defecto sin excepción. → Tareas 1 y 3.
3. Hash de la URL desconocido, vacío, o de una pestaña no habilitada (`#analisis` antes de escanear): cae a `resumen`. → Tarea 3.
4. Componentes sin `datos` o sin `guia` (backend viejo, demostración que falló): fichas con "—" y sin excepción. → Tarea 4.
5. Nombres de dispositivo hostiles (`<script>`, `&`) en el hero, las fichas y la tabla: se muestran como texto, nunca se interpretan; ningún `innerHTML` con datos sin escapar. → Tareas 4 y 5 (prueba de lint de `innerHTML` + pruebas de `modelo.js`).

## Estructura de archivos (decidida)

```
config/palette.css                 tokens de color (claro/oscuro) + espaciado, radios, sombras, tipografía
frontend/templates/base.html       carga los scripts en orden
frontend/templates/index.html      armazón: barra, avisos, pestañas, paneles
frontend/static/css/style.css      estilos por componente (solo usa tokens)
frontend/static/js/estado.js       constantes (NOMBRES_COMPONENTES, CHIP_TEXTO, SEVERIDAD, QUIEN_TEXTO, ETIQUETAS_CAMPOS, DATOS_MOCK)
frontend/static/js/iconos.js       SVG: componentes, estados, interfaz
frontend/static/js/dom.js          escapar(), crear()
frontend/static/js/modelo.js       lógica pura sin DOM (exporta con module.exports si existe `module`)
frontend/static/js/vistas.js       dibujo de cada vista
frontend/static/js/app.js          estado global, API, pestañas, menú, tema, modo, eventos, arranque
frontend/tests/modelo.test.js      pruebas de Node de modelo.js e iconos.js
```
Orden de carga en `base.html`: `estado.js`, `iconos.js`, `dom.js`, `modelo.js`, `vistas.js`, `app.js`.
